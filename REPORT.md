## 1. Резюме (Executive Summary)

Цель работы — спроектировать процесс разработки микросервиса «Расчет корзины
и скидок» системы лояльности: выбрать СУБД, настроить репозиторий и
командные стандарты, внедрить автоматический quality gate, провести
обратное проектирование legacy-кода и спланировать code-review.

Основные результаты:

- По взвешенной матрице решений выбрана **PostgreSQL** (4.65 против 3.55 у MongoDB).
- Создан публичный репозиторий с моделью ветвления `main` → `develop` → `feature/*`,
  добавлены `.editorconfig` и `.github/CODEOWNERS`, ветка `develop` защищена
  правилом «Require a pull request before merging».
- Настроен GitHub Actions workflow `QA` (flake8, длина строки ≤ 80), его
  работа проверена методом «сломать и починить»: статус PR сменился с
  failed на passed.
- Для legacy-функции `calculate_cart_total` построена диаграмма
  деятельности UML, выявлены code smells, подготовлен план ревью с
  измеримыми критериями и механизмом эскалации.

## 2. Сравнительный анализ технологий

Контекст: хранение истории транзакций, начисленных/списанных баллов и
промокодов. Это финансовые данные: важнее всего атомарность и
согласованность (баллы не должны «теряться» или дублироваться), затем
целостность связей (клиент ↔ транзакция ↔ промокод) и стоимость
владения. Гибкость схемы для такой предметной области вторична.

### 2.1. Матрица принятия решений

Шкала оценок: 1 — плохо, 5 — отлично.

| № | Критерий | Вес | Обоснование веса | PostgreSQL | MongoDB |
|---|----------|:---:|------------------|:----------:|:-------:|
| 1 | Поддержка ACID-транзакций | **0.35** | Списание баллов и применение промокода должны выполняться атомарно; ошибка = прямые финансовые потери | 5 | 3 |
| 2 | Целостность данных (строгая схема, FK, CHECK, UNIQUE) | **0.20** | Уникальность промокода, запрет отрицательного баланса на уровне БД | 5 | 3 |
| 3 | Производительность чтения и аналитических запросов | **0.15** | Отчеты по истории транзакций, агрегаты по клиентам | 4 | 4 |
| 4 | Гибкость схемы | **0.10** | Условия акций могут меняться, но базовая модель стабильна | 3 | 5 |
| 5 | Стоимость владения и экосистема | **0.20** | Open source, managed-сервисы, ORM, миграции, специалисты на рынке | 5 | 4 |
| | **Сумма весов** | **1.00** | | | |

Обоснование баллов:

- **ACID:** PostgreSQL — полноценные транзакции с уровнями изоляции вплоть до
  SERIALIZABLE «из коробки» (5). MongoDB поддерживает multi-document
  транзакции с 4.0, но они требуют replica set, имеют ограничения по
  времени/размеру и снижают производительность (3).
- **Целостность:** в PostgreSQL ограничения задаются декларативно (5); в
  MongoDB — только JSON Schema validation, внешних ключей нет (3).
- **Чтение:** обе СУБД быстро читают по индексам; PostgreSQL сильнее в
  JOIN/оконных функциях, MongoDB — в чтении целого документа (4 / 4).
- **Гибкость схемы:** PostgreSQL компенсирует JSONB, но миграции нужны (3);
  MongoDB — schemaless (5).
- **TCO/экосистема:** PostgreSQL — полностью open source (PostgreSQL License),
  богатая экосистема (5); MongoDB — лицензия SSPL, часть функций в Atlas (4).

### 2.2. Расчет и обоснование выбора

Формула взвешенной оценки:

$$Score = \sum_{i=1}^{n} w_i \cdot s_i, \quad \sum_{i=1}^{n} w_i = 1.0$$

| Критерий | Вес | PostgreSQL: w·s | MongoDB: w·s |
|----------|:---:|:---------------:|:------------:|
| ACID | 0.35 | 0.35 × 5 = 1.75 | 0.35 × 3 = 1.05 |
| Целостность | 0.20 | 0.20 × 5 = 1.00 | 0.20 × 3 = 0.60 |
| Чтение | 0.15 | 0.15 × 4 = 0.60 | 0.15 × 4 = 0.60 |
| Гибкость схемы | 0.10 | 0.10 × 3 = 0.30 | 0.10 × 5 = 0.50 |
| TCO/экосистема | 0.20 | 0.20 × 5 = 1.00 | 0.20 × 4 = 0.80 |
| **Итого** | **1.00** | **4.65** | **3.55** |

- PostgreSQL: 1.75 + 1.00 + 0.60 + 0.30 + 1.00 = **4.65**
- MongoDB: 1.05 + 0.60 + 0.60 + 0.50 + 0.80 = **3.55**

**Вывод:** побеждает **PostgreSQL** (отрыв 1.10 балла, ≈ 31%). Решающими
стали критерии с наибольшим весом — ACID и целостность данных, критичные
для финансовых операций с баллами. Преимущество MongoDB в гибкости схемы
имеет малый вес и частично компенсируется типом `JSONB` в PostgreSQL
(например, для хранения произвольных условий акций). Анализ
чувствительности: даже при повышении веса гибкости схемы до 0.30 (за счет
снижения веса ACID до 0.15) PostgreSQL остается лидером (4.25 против 3.95).

## 5. Обратное проектирование и планирование ревью

### 5.1. Анализ алгоритма

![UML Diagram](https://github.com/tenmich/lab1-comprensive-Viktorov/raw/feature/review-plan/docs/uml_diagram.png)

[UML Diagram](docs/uml_diagram.png) (диаграмма находится в ветке
`feature/review-plan`, PR [#3](https://github.com/tenmich/lab1-comprensive-Viktorov/pull/3): [просмотр](https://github.com/tenmich/lab1-comprensive-Viktorov/blob/feature/review-plan/docs/uml_diagram.png))

На диаграмме деятельности отображены начальный и конечный узлы, условие
базовой скидки `cart_sum > 15000`, цикл `for p in promos` с вложенными
условиями `if p == "SUMMER"` / `elif p == "VIP"`, ветвление по уровню
лояльности и финальное ограничение `price < cart_sum * 0.70`.

Выявленные «запахи кода» (Code Smells):

1. **Магические числа** — `15000`, `0.85`, `500`, `0.90`, `0.97`, `0.93`,
   `0.70` зашиты в код без имен и пояснений.
2. **Магические строки** — коды промокодов `"SUMMER"`, `"VIP"` захардкожены;
   добавление акции требует правки кода.
3. **Длинная цепочка условий (Switch Statements)** — `if/elif` по промокодам
   и по `tier` вместо таблицы/словаря правил или паттерна Strategy;
   нарушен принцип Open/Closed.
4. **Отсутствие валидации входных данных** — отрицательная `cart_sum`,
   неизвестный `tier`, `promos = None` не обрабатываются.
5. **Неизвестные промокоды игнорируются молча** — ошибка ввода не видна
   ни пользователю, ни логам.
6. **Повторное применение промокода (уязвимость фрода)** —
   `["SUMMER", "SUMMER", ...]` применяется многократно; спасает только
   потолок 30%.
7. **Деньги во `float`** — накопление ошибок округления
   (например, `0.1 + 0.2 != 0.3`); нужен `Decimal` или расчет в копейках.
8. **Неочевидный порядок применения скидок** — фиксированная скидка
   `-500` до/после процентной дает разный результат в зависимости от
   порядка промокодов в списке (`["VIP", "SUMMER"]` ≠ `["SUMMER", "VIP"]`).
9. **Примитивная одержимость (Primitive Obsession)** — `tier` передается
   как «голое» целое число `1/2` вместо Enum (`LoyaltyTier.SILVER` и т.п.).
10. **Скрытое бизнес-правило** — ограничение «скидка не более 30%» не
    задокументировано и смешано с основной логикой; функция делает
    несколько вещей сразу (нарушение SRP).
11. **Отсутствие тестов и документации** — нет docstring и
    модульных тестов.
12. **Граничное условие `>`** — при `cart_sum == 15000` скидка не
    применяется; неясно, задумано ли так требованиями.

### 5.2. План code-review

Подход: формальная инспекция по чек-листу + асинхронное ревью в PR.
Автоматический gate (`QA / flake8`) отсекает стилевые дефекты, а люди
концентрируются на логике, точности и фроде. Ревью Code Owner обязательно
благодаря `CODEOWNERS` и защите ветки `develop`.

План: [`docs/review-plan.md`](https://github.com/tenmich/lab1-comprensive-Viktorov/blob/feature/review-plan/docs/review-plan.md),
открытый Pull Request: [#3](https://github.com/tenmich/lab1-comprensive-Viktorov/pull/3).

Ключевые измеримые критерии:

| Критерий | Порог |
|----------|-------|
| Магические числа | 0 (все коэффициенты — именованные константы) |
| Валидация входных данных | 100% параметров, `ValueError` при ошибке |
| Покрытие тестами (`pytest --cov`) | > 80% строк и ветвлений |
| flake8 | 0 замечаний (check passed) |
| Цикломатическая сложность | ≤ 5 на функцию |

Механизм эскалации: (1) обсуждение в треде PR, 1 рабочий день → (2)
15-минутная встреча автора, ревьюера и Tech Lead → (3) решение
ответственного по типу спора: бизнес-правила — Product Owner/аналитик,
техника — Tech Lead, безопасность — AppSec (право вето) → (4) фиксация
решения в PR / ADR. Критичные дефекты блокируют слияние.

## 6. Заключение

Настроенные процессы снижают риск внесения дефектов на нескольких
уровнях:

- **Архитектурный выбор** по формальной взвешенной матрице сделан
  прозрачно и воспроизводимо; выбранная PostgreSQL гарантирует ACID и
  целостность финансовых данных на уровне СУБД.
- **Защита ветки `develop` + CODEOWNERS** исключают прямые коммиты в
  интеграционную ветку: каждое изменение проходит через PR и ревью
  владельца кода.
- **`.editorconfig`** устраняет «шумовые» диффы (кодировка, отступы,
  переносы строк) и упрощает ревью.
- **Автоматический quality gate** (GitHub Actions + flake8) детерминированно
  блокирует код с нарушениями — это было продемонстрировано: PR с
  ошибками получил статус failed и стал пригоден к слиянию только после
  исправления.
- **Обратное проектирование** (UML) сделало логику legacy-кода наглядной и
  помогло выявить дефекты (повторное применение промокодов, расчет во
  `float`, магические числа) еще до ревью.
- **План ревью** с измеримыми критериями превращает ревью из субъективного
  мнения в проверяемую процедуру, а механизм эскалации предотвращает
  блокировку работы из-за споров.

В совокупности «сдвиг проверок влево» (shift-left) — от автоматических
проверок до структурированного ревью — позволяет находить дефекты на
самых дешевых для исправления этапах.
