# План code-review: модуль `src/discount.py`

**Объект ревью:** функция `calculate_cart_total(cart_sum, tier, promos)` —
финальный расчет стоимости корзины с учетом базовой скидки, промокодов и
уровня лояльности.
**Тип ревью:** формальная инспекция (по чек-листу) + асинхронное ревью в
Pull Request на GitHub.

## 1. Цели ревью

| № | Цель | Что проверяем |
|---|------|---------------|
| Ц1 | **Точность расчетов** | Денежные суммы не считаются во `float` (используется `Decimal`/целые копейки), определено правило округления (ROUND_HALF_UP до 2 знаков), порядок применения скидок зафиксирован в спецификации. |
| Ц2 | **Защита от фрода** | Невозможно получить отрицательную/нулевую цену; промокоды не применяются повторно (дубли `["SUMMER", "SUMMER"]`); неизвестные промокоды отклоняются, а не игнорируются молча; соблюдается потолок скидки 30%. |
| Ц3 | **Корректность применения скидок** | Скидки применяются в соответствии с бизнес-правилами (база → промокоды → уровень лояльности → ограничение); граничные значения (`cart_sum == 15000`, `tier` вне `{0,1,2}`) обработаны явно. |
| Ц4 | **Сопровождаемость** | Код читаем, расширяем (новый промокод/уровень добавляется без правки `if/elif`), соответствует стандартам `.editorconfig` и `flake8`. |

**Процесс:** PR в `develop` → автоматическая проверка `QA` → назначение
Code Owner → ревью ≥ 1 approve от Code Owner (защита ветки `develop`) →
слияние. Срок первичного ответа ревьюера — 1 рабочий день.

## 4. Эскалация при спорах

1. **Уровень 1 — обсуждение в PR.** Автор и ревьюер обсуждают замечание в
   треде; аргументы подкрепляются требованиями, тестом или ссылкой на
   стандарт. Срок — 1 рабочий день.
2. **Уровень 2 — синхронная встреча (15 мин).** Если консенсус не
   достигнут, автор, ревьюер и Tech Lead (Code Owner) обсуждают вопрос
   голосом. Решение фиксируется комментарием в PR.
3. **Уровень 3 — решение владельца.** Спор о *бизнес-правилах* скидок
   решает Product Owner / бизнес-аналитик; спор о *технической реализации*
   — Tech Lead; спор о *безопасности/фроде* — AppSec имеет право вето.
4. **Фиксация.** Итоговое решение оформляется в PR, при необходимости
   создается ADR (`docs/adr/`) или задача в бэклоге с меткой `tech-debt`.
5. **Критичные дефекты** (неверная сумма списания, возможность фрода)
   блокируют слияние до исправления независимо от сроков.
